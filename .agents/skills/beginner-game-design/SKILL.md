# 从客户的话到游戏规则

读取根目录 `AGENTS.md`、`项目记录/项目概念.md`、`游戏设计.md`、`完整版本范围.md` 和当前任务；遵循 `02_工作流规范/新手沟通与提问规范.md`。

## 从已确定方向继续

类型与已确认体验从项目概念读取；已定不重问，未定才引导选择。按 `02_工作流规范/游戏类型与技术适配.md` 选用相关设计与测试关注点。先按 `02_工作流规范/已有资料接收与理解.md` 读取客户已有世界观、剧情和玩法资料，并给出处。只有资料没有覆盖、确有冲突或用户明确想改时，才追问背景、玩家动作与目标。不要把世界观文档自动视为可执行规则；将已有设定映射到玩家动作和具体场景，缺的机制再补问。没有资料时可从“玩家进入游戏后，最先想做什么？遇到阻碍或成功后，你希望发生什么？”开始。

从一次典型游玩推演：玩家目标 → 观察与输入 → 行动和规则 → 成功/失败/中断反馈 → 后续变化与再次行动。区分客户已决定、AI 建议和待原型验证；状态用 `[Confirmed]`、`[Proposal]`、`[To Decide]`、`[To Prototype]`。

## 形成可以开发的需求

- 每个功能写玩家价值、输入和前置条件、规则和优先级、正常/失败/重复/中断、数据所有者、表现和可观察验收。规模小则合并叙述，不强制重型架构。
- 具体规则覆盖所选机制的正常、异常、重复、中断与恢复路径；动作测输入/碰撞，解谜测可解性/重置，经营测资源/时间，其他类型按适配规范选用，不套用无关机制。
- 若包含叙事，写触发条件、玩家知道什么、选择如何记忆、后果何时兑现、分支收束和关键结局可达性。先做一个完整事件再批量写剧情。
- 用 `项目记录/内容与资产矩阵.md` 管全部约定内容单位（关卡/对局/章节/案件等）、规则、资产及测试。没有客户依据，不编造数量、预算或发布日期。
- 原型用于验证循环；代表片段验证生产方法；完整版本范围是独立的最终承诺。必须包含从开始到约定完成条件或可重复游玩的完整闭环、产品配套和交付标准。

## 不确定与变化

遇到节奏、教学、道德选择、信息负担、叙事呈现、内容成本等不确定，主动读取 `beginner-game-reference`。将“观察事实、原因推断、我们的建议”分开。只有已授权的低成本实现细节可自行决定；创作方向变化交给客户，体验争议用小实验。

变更先读 `02_工作流规范/任务拆分与需求变更.md`。更新当前权威规则，再追踪实现、内容、测试和已验收阶段；保留受影响的旧版证据。验收前独立检查规则一致性及必要性，不能用“客户看过文案”替代游戏体验证据。

## 从想法到可承担的完整范围

进入范围确认与代表片段复核时读取 `02_工作流规范/范围估算与制作校准.md`。不要直接把内容数量估算交给新手。先提取已有设定和投入限制，给少量具有完整体验闭环的选项；区分暂定计划与批量制作确认，用样本实际成本校准。完整范围和内容矩阵映射制作批次，按 `02_工作流规范/当前操作卡与内容生产.md` 建依赖。
